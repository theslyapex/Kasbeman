## Production dependency discovered

The hosted Supabase project `xitrazjbemmkarawejfe` currently contains these public base tables:

`branches`, `business_invitations`, `business_members`, `businesses`, `member_role_assignments`, `permissions`, `profiles`, `role_permissions`, `roles`.

It does **not** yet contain `customers`, `tickets`, `ticket_comments`, or `ticket_events`.

The canonical ticketing migration:
- defines `tickets.customer_id` with a composite foreign key to `customers(business_id,id)`;
- relies on `customers` in the web ticket page and create-ticket flow;
- must be applied after the CRM customer migration and its tenant-scoped unique key.

The sales/inventory core now has canonical migration `supabase/migrations/20261128124834_sales_inventory_core.sql`, generated by Supabase CLI 3.4.0 and tested in disposable PostgreSQL 17 CI and local Supabase. The CRM customer foundation is isolated in canonical migration `supabase/migrations/20261128124155_crm_customer_core.sql`, generated by Supabase CLI 3.4.0 and tested in disposable PostgreSQL 17 CI. It has not been applied to production. Therefore, ticketing still cannot be deployed independently: its migration must follow CRM, and the web route must wait until both required schemas exist.

## Required rollout order

1. Review the canonical CRM and ticketing migrations against the exact hosted migration baseline and helper signatures.
2. Run the full PostgreSQL 17 canonical migration, schema, tenant-isolation, permission-negative, invitation lifecycle, FK and multi-connection concurrency suites (passing in CI; rerun before rollout).
3. Verify web and mobile against a disposable/staging Supabase stack using authenticated users with owner, branch operator, editor, and restricted comment permissions.
4. Verify Data API exposure, generated client types, and security/performance advisors in staging.
5. Review the complete migration sequence and deployment plan. Production application requires explicit user approval.

## Release blockers / safeguards

- Ticketing canonical migration exists and passed PostgreSQL 17 CI plus local Supabase integration, but has not been applied to production.
- CRM canonical migration exists and passed PostgreSQL 17 CI plus local Supabase Auth/Data API integration, but has not been applied to production.
- Do not add a placeholder customer table to production merely to satisfy the ticket foreign key.
- Do not disable or weaken the customer foreign key, RLS, or permission guards to bypass the dependency.
- Keep all work on `foundation/bootstrap`; do not merge to `main` without explicit authorization.
- Recheck the hosted migration history immediately before any production rollout.

## Current conclusion

Ticketing implementation, canonical migration and CI coverage are in place. The combined canonical CRM, ticketing and sales/inventory stack now passes disposable PostgreSQL 17 CI and a local Supabase stack with real Auth/Data API, but the modules are **not production-ready for deployment** until the hosted baseline is reviewed, hosted staging is verified, and web/mobile clients pass live E2E. No production schema changes have been applied. CI does not prove that the modules can be applied to the current hosted production schema.
