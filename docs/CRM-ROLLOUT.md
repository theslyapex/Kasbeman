# CRM Customer Core — Rollout Notes

## Current state

The customer foundation has a canonical Supabase migration:

- Draft source: `supabase/drafts/crm_core.sql`
- Canonical migration: `supabase/migrations/20261128124155_crm_customer_core.sql`
- The filename was generated by Supabase CLI 3.4.0 using `supabase migration new crm_customer_core`.
- The canonical migration is applied by `scripts/test-postgres-schema.sh` in the disposable PostgreSQL 17 CI harness.
- It has **not** been applied to the hosted production project.

The sales/inventory draft references the CRM-owned `public.customers` table but no longer creates that table or its policies. Ticketing continues to depend on the customer composite key `customers(business_id, id)`.

## Dependencies and hosted baseline

- `public.businesses(id)` from the existing identity/tenancy foundation.
- `auth.users(id)` for the creator reference.
- `private.has_business_permission(uuid, text, uuid)` from the existing RBAC foundation.
- The four permission keys `crm.customers.read/create/update/delete` already exist in the hosted permission catalogue.
- The hosted migration history was read-only checked and contains the five existing identity/RBAC/rate-limit/membership migrations. No CRM migration is recorded there.
- The hosted database currently has no `public.customers` table and no production customer data.

## Security model

- Every customer row has a required `business_id`.
- Unique key `(business_id, id)` supports tenant-scoped foreign keys from future modules.
- RLS gates select, insert and update independently.
- Insert requires `crm.customers.create` and `created_by = auth.uid()`.
- Profile updates require both `crm.customers.read` and `crm.customers.update`.
- Status changes require `crm.customers.delete`; this permission is intentionally reused as archive/restore authority, not a direct DELETE grant.
- The trigger rejects business reassignment and has direct execute revoked from API roles.
- No direct DELETE grant is given to `authenticated` or `anon`.

## Application surfaces

- Web route: `/dashboard/[businessId]/customers`
- Web server actions: `apps/web/src/app/actions/customers.ts`
- Web UI: `apps/web/src/app/dashboard/[businessId]/customers/customers-panel.tsx`
- Flutter screen: `apps/mobile/lib/src/inventory/customers_screen.dart`
- The web interface supports create, search, profile edit, archive and restore; action visibility follows CRM permission keys.
- The Flutter customer screen's edit/archive controls now require the same read/update/delete permission combination as the database.
- Customer financial details remain separately gated by finance permissions in the mobile client.

## Required production rollout

1. Review the canonical migration against the exact hosted migration baseline and helper signatures.
2. Run the full PostgreSQL 17 schema, tenant, permission and concurrency suite against a clean disposable database.
3. Apply to a staging Supabase project and verify authenticated owner/admin/member/editor/create-only behavior through the Data API.
4. Verify the dependent sales/inventory and ticketing migrations are sequenced after CRM and pass their integration tests.
5. Review the complete migration and deployment plan. Production application requires explicit user approval.

Do not create a placeholder customer table, disable RLS, relax composite foreign keys or bypass the permission guard to make downstream modules install.

## Release gate

The canonical CRM migration is generated and has passed both the combined PostgreSQL 17 suite and local Supabase Auth/Data API integration alongside ticketing and sales/inventory. It has not been applied to production. No hosted staging environment or live web/mobile client E2E test has been established. The public deployment remains unconfigured, and `main` remains untouched.
